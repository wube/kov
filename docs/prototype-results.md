# Speed-test prototype: results

Date: 2026-10-23. Machine: PC-PRACOVNA, AMD Ryzen 9 9950X (16 cores / 32 threads), 128 GB RAM,
Windows 10. Compiler for kovc: clang-cl 19.1.5, Release.

## Question

Can a compiler front end that never processes an `#include`, parses all files in parallel into one
shared in-memory model and resolves names order-independently, handle a Factorio-sized code base
in a fraction of a second? This is the core bet of Kov (see [design.md](design.md)).

## What was built

`kovc` (about 5,500 lines of C++20 in `compiler/src/`):

1. **Lexer** (`lexer.cpp`): one pass, no preprocessor; a `#` line becomes one token. Identifiers
   are interned into a shared, sharded symbol table.
2. **Parser** (`parser.cpp`): recursive descent for the Kov subset, tolerant of C++ so that the
   real Factorio sources can be used as the corpus. It builds a full AST (declarations,
   statements, expressions, types) into a per-file arena. Where C++ needs semantic knowledge to
   parse (`a * b;`, `x < y > z`), it uses syntactic heuristics. Preprocessor conditionals keep
   their first branch (`#if 0` keeps the else branch); ALL_CAPS identifiers in declaration
   position are treated as macros.
3. **Resolver** (`resolver.cpp`): phase 1 indexes every file's declarations into one shared scope
   tree (namespaces merged across files, class and enum scopes, sharded locks). Phase 2 walks all
   declarations and function bodies and resolves type names and identifiers against that tree:
   locals, parameters, template parameters, class members including inherited ones (base classes
   are resolved lazily and memoized, thread-safe), `using` aliases and directives, qualified names.
   Phase 2 is read-only on the tree and needs no locks.

Not done, on purpose: type checking. `a.b` / `a->b` needs the type of `a`; those member accesses
are counted as "deferred". Template instantiation and constexpr evaluation are not touched.

## Corpus

Factorio's own C++: `C:\Factorio\src`, `tests`, `libraries\CommonUtil`, `libraries\Agui`.
8,100 files, 54 MB, **1.33 M lines**, 8.4 M tokens, 99k distinct identifiers.
The standard library, the C libraries (SDL, Lua, zlib...) and the other third-party libraries are
*not* in the corpus, so names from them are unresolvable by construction.

### Comparison with clang

`compiler/bench/clang_syntax_only.cmd` runs `clang-cl /Zs` (parse + full semantic analysis, no code
generation) on a random sample of 40 Factorio `.cpp` files with the include paths and defines
from `fastbuild/fbuild.bff` (FastDebug configuration), without the precompiled header. All 40
compile cleanly. Results (`compiler/bench/clang_syntax_only.result.txt`):

| | clang-cl /Zs, per translation unit | kovc, whole code base |
|---|---|---|
| one file, sequential | mean **1.09 s** (0.42-2.0 s) | |
| 40 files, 40 parallel processes | 4.63 s wall | |
| all 3,230 `.cpp` files, extrapolated | 3,500 CPU-s; ~110 s wall at ideal 32x scaling, ~370 s at the measured parallel rate | **0.32 s wall, 1.2 CPU-s** |

Why the gap is so large: each translation unit re-reads and re-parses its headers (several
hundred thousand preprocessed lines per `.cpp`), so clang processes the same declarations
thousands of times; kovc reads every line once. This is exactly the cost Kov's model removes.

What the comparison does *not* show: clang also type-checks every expression and instantiates
every template, which kovc does not do yet. That work is proportional to the amount of code,
not to the number of translation units, so it is expected to cost seconds, not minutes, when
done once.

### Comparison with the real Factorio build

The practical reference point is Factorio's real build, which already hides most of the header
cost with unity builds (100 files per unit), a PCH and FASTBuild. Measured on this same machine
(Debug x64, MSVC 14.44; setup and method in [factorio-build-baseline.md](factorio-build-baseline.md)):

| Factorio build (MSVC, Debug x64, FASTBuild) | time |
|---|---|
| clean rebuild, 919 objects | 62 s |
| unit tests, `--fork`, 9,012 passing | 59 s |
| one-line edit in an ordinary header, rebuild + link | 16 s (about 10 s of it linking) |
| one-line edit in a header included by `Common.hpp` (the PCH) | 55 s |

Against that, the prototype front end processes the whole code base in 0.32 s, and it does so
from scratch each time; the design's persistent compiler would re-resolve only what an edit
touches. The missing pieces before this becomes a like-for-like number are type checking,
template instantiation and code generation, where the Kov design wins by generating each
instantiation once and by never linking; the Factorio numbers above say that linking alone is
10 of the 16 seconds of an incremental build today.

## Stage 2: type checker (2026-10-23, later the same day)

On top of the resolver: canonical interned types (`types.cpp`), declared types with template
parameter substitution, and a type for every expression in every function body
(`resolver.cpp`, the `Walker`). Overload selection is by argument count only, there are no
implicit-conversion rankings yet, and template bodies are not re-checked per instantiation.

| Phase (32 threads) | before | with type checking |
|---|---|---|
| index | 0.013 s | 0.014 s |
| resolve + check | 0.030 s | **0.028 s** (0.31 s single-threaded) |
| whole front end, wall time | 0.32 s | 0.33 s |

Typing 1.94 M expressions costs about 0.2 s of CPU in total; it is invisible in the wall time.
The type table ends with 42,862 distinct types for the whole code base.

What the checker could determine on Factorio:

| | count | result |
|---|---|---|
| member accesses `a.b`, `a->b`, `this->b` | 461,697 | **78.9% bound** to a declaration, 4.5% dependent on a template parameter, 16.3% object type unknown, 0.3% no such member |
| expressions | 1,936,622 | **77.8% typed**, 2.8% dependent, 19.4% unknown |
| calls | 219,572 | resolved to a function (43k had several candidates with the same arity, mostly const/non-const pairs) |
| type names | 273,439 | 84.3% resolved (fixed-width integer names count as builtins), 2.8% dependent, 12.9% unresolved |

The unknowns are what the corpus cannot answer, not what the checker cannot do: the members
accessed on objects of unknown type are `size`, `empty`, `second`, `c_str`, `push_back`,
`emplace_back`, `reset`, `first`, `begin`, `end` (std containers, smart pointers and pairs, not
in the corpus), the unresolved names are `assert`, the Lua C API and macro-generated

unknown expressions, 52k are unresolved names, 75k an unknown object type, 11k `auto` variables
initialised from such expressions, 6k constructs not modelled yet (brace initialisers,
`typeid`, folds).

Not done at this stage: implicit conversions in overload resolution, members inherited through
templated bases (`Derived<int> : Base<T>` currently stays dependent), constexpr evaluation.

## Stage 3: template bodies checked once per instantiation (2026-10-23)

This is the proposal's template model made concrete: an instantiation is a (template,
arguments) pair; the first thread that needs it claims it in a shared registry and checks the
bodies, any other thread finds it done or in progress and only waits if it needs a result (the
deduced return type of an `auto` function). Class template instantiations check every member
function body, including out-of-line `void Foo<T>::f()` definitions, which the indexer now
attaches to their class. Function template instantiations check the body with the deduced
arguments plus the class arguments of the object they were called on.

| | |
|---|---|
| class template instantiations checked | 953 |
| function template instantiations checked | 3,166 |
| requests that found the work done or in progress | 59,702 requests in total, 0 waits |
| member bodies checked inside instantiations | 17,001 |
| expressions typed inside instantiations | 293,899 (62% typed, 9% dependent, 29% unknown) |
| CPU spent on instantiation checking | 0.06 s single-threaded, 0.16 s summed over 32 threads |
| resolve + check + instantiate, wall time | **0.031 s** on 32 threads, 0.33 s single-threaded |

So for Factorio, "each instantiation exactly once" is about 4,000 instantiations and 17,000
bodies, and it costs less than a tenth of a second of CPU. The remaining dependent and unknown
expressions inside instantiations come from templated base classes, member templates and the
same std-library holes as everywhere else. Two simplifications to remove later: expression types
are stored on the shared AST node, so the last instantiation checked wins (a per-instantiation
side table is the proper home), and the member-body check does not yet record diagnostics per
instantiation.

## Stage 4: a Kov program runs (2026-10-23)

`compiler/src/codegen.cpp` turns the checked program into textual LLVM IR for the whole program
and `kovc --exe out.exe program.kov` hands it to the bundled clang (`clang -O2 out.exe.ll`),
which does the optimisation, machine code and linking. No LLVM libraries are needed on the
machine. The subset covered is the one in design.md, "Kov v0": functions, structs with
methods and single inheritance, enums, the arithmetic types, pointers, references, arrays,
globals, `new`/`delete`, all control flow including `switch`, `extern "C"` functions.

Tests: `compiler\tests\run_tests.cmd` compiles every `tests/run/*.kov`, runs it and compares the
output with the `.expected` file. Eleven programs so far (hello, control, types, structs,
objects, templates, strings, virtual, lambdas, containers, format).

Object model (added the same day): constructors with member initializers and default member
initializers, destructors, destruction at scope exit in reverse order including the scopes left
by `return`, `break` and `continue`, copy constructors (or memberwise copy), temporaries destroyed
at the end of the full expression, `operator[]`, `operator=`, `operator+` and friends as members,
class return values through a hidden result slot, class parameters as caller-made copies owned
by the callee, `new`/`delete` of objects. `objects.kov` checks all of it with a live-object
counter.

| step for `hello.kov` | time |
|---|---|
| kovc: lex, parse, resolve, check, IR | about 1 ms |
| clang: optimise, codegen, link | 0.07 s |

Templates in generated code (same day): a struct layout per instantiation type, instantiated
functions emitted on first use from a worklist after the checker re-types the body for the
concrete arguments, class and function templates with deduced or explicit arguments, member
templates of class templates, destructors of instantiations. IR names carry the arguments:
`@"Vector<int32>::push_back(const int32&)"`, `@"Vector<int32>::sumAs<int64>()"`.
`templates.kov` exercises a `Vector<T>` for two element types and function templates.

Standard library seed (same day, `stdlib/core/`): `String` (one UTF-8 class, zero-terminated,
no traits or allocator parameters) and `Vector<T>` (growable, elements relocated bitwise), both
written in Kov v0 and compiled from source with every program; `kovc` adds `stdlib/` next to
the compiler automatically (`--std DIR`, `--no-std`). `strings.kov` builds strings, copies
them, stores them in a `Vector<String>`, iterates with range-for and checks that everything is
destroyed. Needed in the code generator for this: range-for over arrays and classes with
pointer-returning `begin()`/`end()`, placement `new`, explicit destructor calls (`x.~T()`).

Overload resolution with conversion ranking followed (exact, qualification, promotion,
standard conversion, user-defined through non-explicit constructors and conversion operators;
C++'s "better in one argument and not worse in any" rule, non-templates preferred, const
methods matched to const objects), shared by the checker and the code generator's constructor
and operator selection. `String` now has four `append` overloads and two `operator+=`. On
Factorio, calls with several same-arity candidates went from 48,504 to 14,085 still-ambiguous
ones (mostly identical signatures from macro-generated code); the resolve+check phase costs
0.086 s on 32 threads with ranking instead of 0.032 s, which is worth optimising later by
caching each class's conversion constructors.

Virtual functions (same day): a polymorphic class carries a vtable pointer at offset 0 (its own,
or its first base's), slots are inherited and extended in declaration order, overrides are
matched by name, parameter types and constness (`override` or an inherited slot), constructors
store the vtable pointer after the bases are built, pure virtual slots are null, and `delete`
through a base pointer dispatches to the virtual destructor. `virtual.kov` covers dispatch
through pointers and references, a virtual destructor, a pure virtual method and a non-virtual
method calling a virtual one. A polymorphic base must be the first base (no secondary vtables).

Lambdas (same day): the parser reads the capture list and gives every lambda a closure identity
(a synthetic class `__lambda_N`), so a lambda's type is unique and templates instantiate once
per lambda. The code generator builds a closure struct from the captures (by copy, by
reference, `this`, or the defaults `[=]`/`[&]`, whose capture set is found by scanning the
body for enclosing locals), emits the lambda's function right where the lambda appears, and
calls closure values directly: `@"__lambda_3::operator()(int32)"`. `lambdas.kov` stores
closures in variables, passes them to `apply` and `forEach` templates and captures `this` in a
method. Init-captures and generic lambdas came later (the latter on 2026-10-25, see
path-to-factorio.md); not yet: conversion to function pointers.

Library, second round (same day): `Hash.kov` (`hashOf` overloads for the integers and `String`,
FNV-1a), `Optional<T>`, `HashMap<K, V>` (open addressing with linear probing, `insert`, `find`,
`operator[]`, `erase`, `forEach` with a lambda, copy and assignment) and `Format.kov`
(`toString` for integers, doubles, bools and strings, `print`, `println`). The code generator
gained implicit memberwise copy construction and copy assignment for classes whose members
need them, zero-initialisation of scalar members left out of a constructor, and `T(args)` for
a template parameter `T`. `containers.kov` exercises a `HashMap<String, int>`, a
`HashMap<int, String>` with 100 entries and a copy, `Optional<String>` and the conversions.

Variadic templates (same day): a parameter pack deduces to a `Pack` type whose elements become
separate parameters; `args...` in a call and fold expressions expand by re-typing the pattern
once per element (so `toString(args)` picks a different overload for each element), and
`sizeof...` is a constant. With that the library has a type-safe `format("{} and {}", a, b)`
plus `print`/`println` overloads taking a pattern; `format.kov` tests packs, folds over `+`
and a join written with a comma fold.

Not in v0 and reported as "codegen does not support X yet": exceptions, multiple
polymorphic bases, arrays of objects with constructors, globals with constructors, more than
four template parameters per function, class-typed iterators in range-for, packs in the middle
of a parameter list. IR names are the
qualified Kov names with parameter types in quotes (`@"Point::move(int32, int32)"`), so there is
no mangling scheme.

## C header import (2026-10-23)

`extern "C" import "stdio.h";` makes the compiler run clang's preprocessor over all imported
headers at once (`clang -x c -E -P`, plus `-E -dM` for the macros), parse the result in C mode as
one more file of the program, and turn constant-looking object-like macros into `const auto`
declarations. The preprocessed text is cached by content hash under the temp directory
(`kov-imports`), so the preprocessor runs once per header set, not once per build.

| import                              | declarations | parse errors | first build | cached  |
|-------------------------------------|-------------:|-------------:|------------:|--------:|
| stdio.h, string.h, math.h, stdlib.h |        3,575 |            0 |     0.085 s | 0.002 s |
| windows.h, stdio.h                  |       40,678 |           17 |     0.195 s | 0.033 s |

(The `imports:` line of kovc. The first-build time is the two clang invocations; the cached time
is reading, lexing and parsing the preprocessed text on one thread.)

`cimport.kov` uses `snprintf`, `sqrt`, `fopen`/`fprintf`/`fscanf`, `malloc`/`free`, `abs` and
the macros `EOF` and `BUFSIZ`; `winapi.kov` uses `QueryPerformanceFrequency` on a
`LARGE_INTEGER` (a union with an anonymous struct), `GetSystemInfo` (an anonymous union inside a
struct), `GetProcessHeap`/`HeapAlloc`/`HeapFree` with `HEAP_ZERO_MEMORY` and `MAX_PATH`. Inline
functions in the headers (`snprintf`, `printf` and friends in the UCRT) are declared, not
compiled; the link line adds `legacy_stdio_definitions` so they resolve.

What the C text needed from the front end: unions and anonymous struct/union members in codegen
(a union is one block of storage, every member at offset 0), `typedef struct { ... } Name;`,
synthetic names for `struct { ... } x;`, `(void)` parameter lists, `unsigned __int64` folded into
the builtin type, MSVC calling conventions dropped from the token stream in C mode, and the
macro-specifier heuristic switched off there (it was skipping `LONG` in `LONG const*`, the cause
of 119 of the original 144 `windows.h` errors). The remaining 18 are `static` after
`__declspec`, `POINTER_32` and a few expression forms; none affected the programs. `--errors N`
lists them. (Declaration counts as of 2026-10-24, after the macro filter learned to keep `_A_SUBDIR`
and drop SAL annotations whose bodies are calls.)

One grammar decision fell out of it: `QueryPerformanceFrequency(&frequency);` parsed as a
declaration of a reference `frequency` of type `QueryPerformanceFrequency` (the C++ reading of
`T (&x);`). Kov now treats `f(*p);` and `f(&x);` as calls and accepts a parenthesised declarator
only when `(` or `[` follows it (`R (*f)(int)`). On Factorio this turned two misparsed files into
clean ones (208 errors in 59 files, 99.27% clean) and changed nothing else: parse 0.074 s,
resolve 0.078 s, 78.2% of member accesses bound, 76.4% of expressions typed. 13 run-tests pass.

## Macro replacements, first batch (2026-10-24)

The small items of design.md section 7, all in one round: `assert(expr);` and
`release_assert(expr);` as statements, `CallerLocation here = caller` default arguments,
`conditional(expr)` functions, `--config name=value` / `--release` as a generated `config`
namespace, `if constexpr` folded at statement scope and evaluated by the parser at namespace and
class scope, `requires <condition>;` at the top of a file, `_` locals, `[[noinline]]` and
`[[forceinline]]`. Default arguments in general were missing from codegen and came with it.

`asserts.kov` covers all of them; a failing assert prints
`fail.kov:4:3: assertion failed: items > 5 && items < 10` on stderr and aborts (the default
`kov_assert_failed`, which a program may replace by defining it `extern "C"`); the same program
built with `--release` runs through, since `assert` compiles to nothing there. 14 run-tests pass.

On Factorio the only change is the intended one: `assert` and `release_assert` statements are
parsed as such and their conditions typed, so the two names left the unresolved list (identifiers
unresolved 41,476 -> 34,494 in the "other" group, expressions typed 76.4% -> 76.9%); parse
0.075 s, 99.27% of files clean, resolve 0.075 s, unchanged.

## First real program: kovlex (2026-10-24)

`programs/kovlex/kovlex.kov` is the Kov lexer written in Kov: 575 lines, the C++ lexer of
`compiler/src/lexer.cpp` ported line for line (symbol table over slices of the file texts, the
same token layout without the bit fields, a directory walk through `io.h`, timing through
`windows.h`). It needed one compiler fix on the way: the C importer dropped every macro with a
leading underscore, so `_A_SUBDIR` did not exist; now only `__`-prefixed names stay out.
kovc compiles it with the standard library (10 files, 1,132 lines) in 15 ms of its own work
(parse 2 ms, index 5 ms, resolve 6 ms, codegen 2 ms; the cached `windows.h` import adds 34 ms),
then clang spends 0.19 s on the 156 KB of IR.

To separate code quality from algorithm, `kovlex.cpp` is the same program transliterated to C++
(`std::vector`, `std::string`, `#include`), built with the same clang at -O2
(`build_cpp.cmd`); `run.cmd` builds and times everything. On the Factorio corpus, one thread:

| lexer | lex time | throughput | counts |
|---|---:|---:|---|
| kovlex, Kov | 0.139 s | 390 MB/s, 60.7 M tokens/s | 1,326,156 lines, 8,440,831 tokens, 98,907 identifiers, 0 errors |
| kovlex, C++ transliteration | 0.144 s | 376 MB/s, 58.6 M tokens/s | identical |
| kovc's lexer, `--lex-only -j 1` | 0.743 s | 73 MB/s, 11.4 M tokens/s | identical (plus the generated config file) |
| kovc's lexer, 32 threads | 0.076 s | 716 MB/s | |

(Three runs each, best shown; the spread is 0.139-0.142 s for Kov and 0.143-0.145 s for C++.
Both binaries are 191,488 bytes.)

So the code Kov generates for this program is the code clang generates for the C++ version: same
backend, same instructions, within 3%. The 5x gap to kovc's own lexer is the thread-safe design
of that lexer (a sharded `unordered_map` behind a `shared_mutex`, two lookups per word, a vector
per file), not the language, and it says that lexer could be several times faster on 32 threads
too.

What the program exercised in Kov v0 for the first time together: C imports of four headers
with their structs and constants, `Vector<T>` of structs and of `String`, references and
pointers to members through `this->`, `switch` on characters, 64-bit arithmetic, `static`
methods, default member initializers, recursion over directories, `main(argc, argv)`.

## Real enums and nameof (2026-10-24)

Design.md section 8.4 as far as it goes without `Optional`: the values in their own brace block,
methods in which `this` is the value, generated `count`, `values` and `str()` (a hand-written
`str()` wins), `switch` on such an enum that must name every value (compile error: `switch on
Light does not handle Amber`) and aborts on a value outside them (`e2.kov:5:3: assertion failed:
invalid value in switch on Light`, through the same `kov_assert_failed`), and `nameof(x)`.
`enums.kov` covers them; 15 run-tests pass. In the compiler: the parser synthesises the three
generated members with `Decl::builtin` markers, the resolver types `this` in enum scopes as a
reference to the enum and gives `values` the array type `E[count]`, codegen folds `count`, emits
`values` as a constant array and `str()` as a switch, and passes the enum value by address as
`this`. Factorio unchanged (0.075 s parse, 99.27% clean, 0.081 s resolve).

## Backend at scale: first measurement (2026-10-24)

`compiler/bench/synth_program.py N` generates N modules of 10 classes each (fields, a
constructor, five arithmetic methods, two virtual overrides of a shared base, a method using
`Vector<int>` and calling a class of the next module, one `runModule` function per module, a
`main` that touches everything), about 300 lines per module, inside the v0 subset. kovc compiles
it into one IR module; clang is then timed on that module alone, single-threaded, with the
32-thread machine otherwise idle:

| classes | lines | functions | IR | kovc, all phases | clang -O0 | clang -O1 | clang -O2 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 7.7 k | 965 | 1.5 MB | 0.016 s | | | 1.40 s |
| 500 | 38 k | 4,605 | 7.3 MB | 0.053 s | 0.37 s | 5.4 s | 6.7 s |
| 2,000 | 154 k | 18,255 | 29 MB | 0.21 s | 1.22 s | 22.1 s | 26.8 s |
| 8,000 | 615 k | 72,855 | 117 MB | 0.84 s | 4.98 s | | 108.8 s |

(kovc's 0.84 s at 8,000 classes is parse 0.037 + index 0.011 + resolve 0.064 + codegen 0.728,
the last single-threaded. At -O0, 4.72 s of the 4.98 are compilation and 0.25 s the lld link.
Peak working set: kovc 596 MB, clang -O0 1,349 MB. Everything scales linearly with size.)

The 8,000-class program has as many function bodies as Factorio (73 k against 71 k), so per
function LLVM costs about 65 microseconds at -O0 and 1.5 ms at -O2, and the whole front end
plus IR writing about 12 microseconds. What follows for the design:

- The code generator must be parallel per file, each file its own module text, which is also
  what lets the LLVM side run in parallel. On 32 cores a Factorio-sized debug build would then
  be about 0.3 s of front end, a few hundredths of codegen and 0.2 s of LLVM -O0 plus the link,
  against 62 s today; a release build about 4 s of -O2 plus the link, against minutes.
- Debug builds can stay on LLVM -O0 for now; an own fast backend only pays once everything
  else is below a second.
- Release builds are LLVM -O2 and nothing else: per-function caching keyed by the IR text (the
  incremental case) and cross-module inlining (a ThinLTO-like pass over the per-file modules)
  are the two things worth doing there, in that order.
- Memory is not a concern at this size.

**Per-file modules (same day).** kovc now emits one IR module per group of files (two groups per
thread by default, `--modules N` to choose; `--emit-llvm` still writes one module) and compiles
them with clang in parallel, -O0 for debug and -O2 for release builds, then links through a
response file. Functions go to the module of their file, instantiations to the module of the
function that asked for them; globals, vtables and the generated functions are `linkonce_odr` in
a comdat so that every module can carry what it uses, and each module declares the functions it
calls from the others. On the 8,000-class program, 32 threads: codegen 0.95 s (still
single-threaded; the IR grows to 148 MB because struct types are repeated in every module),
clang -O0 0.49 s plus 0.12 s of link, so the whole debug build is 1.7 s from source to
executable; release 3.67 s plus 0.13 s of link. Against the single module: 5.0 s to 0.6 s at
-O0, 109 s to 3.8 s at -O2. The test suite compiles about twice as fast as before.

**Unchanged modules keep their objects (same day).** The driver hashes each module's text (with
the optimisation level) and skips clang for a module whose hash and object file are still there.
On the 8,000-class program, debug: a fresh build 1.76 s; a rebuild with nothing changed 1.25 s
(64 of 64 modules unchanged, 0.12 s of link); a rebuild after a one-line change in one file
1.25 s (63 unchanged, one module compiled in 0.10 s). Of that 1.25 s, 0.93 s is the
single-threaded IR writing and 0.10 s the front end, so the one-line-change rebuild of a program
with Factorio's number of functions is 1.25 s against Factorio's 16 s, and the next thing to
make parallel is the IR writing itself. (The same cache serves release builds: a one-line
change costs one module's -O2, about 0.3 s, instead of 3.7 s.)

## Exceptions (2026-10-24)

`throw`, `try`/`catch` (by reference, by value, by base class, `...`), `throw;` and nested
handlers work, with destructors of locals and temporaries running while unwinding, `return` and
`break` out of handlers, and exceptions crossing several frames; `compiler/tests/run/exceptions.kov`
covers all of it and passes in debug and `--release` builds. The implementation is Windows SEH
(`__C_specific_handler`, `RaiseException`, LLVM's `catchswitch`/`catchpad`/`cleanuppad`), about
550 lines in codegen.cpp plus 150 lines of runtime IR emitted into every program that throws;
design.md section 9 records the rules that follow from it.

Two things cost most of the day and are worth knowing before touching this again:

- **Every call inside a catch handler needs the `"funclet"` operand bundle.** One `malloc` call
  without it made LLVM treat the whole handler as unreachable and replace it with `int3`; the
  program died with a breakpoint exception and no message. All calls now go through one helper.
- **A catch handler must not start at a call's return address.** The SEH scope table covers
  `[call, return address]`; when the handler label sits exactly at the return address the
  runtime takes the unwind for a jump within the scope and skips the cleanups (destructors) in
  between. LLVM lays the handler out there whenever the code after the call is `unreachable`,
  including after calls to functions it has *inferred* noreturn (a function whose paths all
  throw). So kovc emits no `unreachable` after a throw: the raise functions are declared as
  returning, the code after a throw stays, and no function is ever provably noreturn. Found
  with a vectored exception handler printing every exception code: `0xE0000001`, then
  `0x80000003`.

## CommonUtil runs (2026-10-25)

The converted `libraries/CommonUtil` (21 Kov files, 4 of them with hand-written parts) compiles
with no code generation complaints, links, and `programs/factorio/tests/smoke.kov` runs against
it with the expected output: `programs/factorio/convert.cmd` does the whole cycle. The front end
numbers on the Factorio corpus did not move (99.27% of files parse, 76.8% of expressions typed).
The road there is in docs/path-to-factorio.md; two findings belong here:

- **The parser split `>=` as a template close**, so `index < 0 || index >= this->length` became
  the assignment `index<0 || index> = this->length`, in the library's own `String::erase` among
  others. Only `>>` may be split (C++11's rule). Found by running converted code, not by
  compiling it: compile-time statistics cannot see a miscompile. The smoke test is now part of
  the conversion check for that reason.
- **Lenient conversions hide bugs.** A pointer passed where an integer parameter was expected
  was converted with `ptrtoint` and the call picked an unrelated overload (`erase(begin, it)`
  became `erase(int, int)` with addresses). Code generation now refuses pointer-to-integer and
  integer-to-pointer argument conversions, as C++ does.
- **Overload resolution without value categories moves from lvalues.** The resolver ranked by
  type alone, so `Function<int(int)> h = f` and `apply(f, 6)` chose `T(T&&)` over
  `T(const T&)` and emptied `f`; code generation's own copy helper did the same by taking the
  last same-class constructor. Found by the `function` test crashing, not by any statistic.
  Lvalue arguments now present themselves as `T&` (so `T&&` is not viable and a forwarding
  `T&&` deduces `U&`), xvalues (`move(x)`) and temporaries move, and the copy helper only ever
  calls a copy constructor. `moves.kov` counts copies and moves against the C++ answer.

## Lessons

- **Windows memory allocation serialises parallel work.** The first parser version allocated and
  zeroed a 1 MB arena chunk per file: 0.8 s of memset and a parse that did not scale past 1.5x.
  Sizing the arena from the token count fixed both (0.72 s -> 0.06 s on 32 threads). The
  persistent-compiler model in the design will reuse memory across builds and avoid this class of
  cost entirely.
- **Parse still plateaus at 8 threads** (0.055 s) while lexing scales to 10x. The remaining
  limit is most likely page-fault throughput on 256 MB of fresh memory; worth measuring with a
  pre-faulted arena pool before optimising anything else.
- **C++ cannot be parsed without semantics; Kov should not inherit that.** `T * x;` vs `a * b;` and
  `f < a > (b)` need to know whether `T`/`f` is a type/template. The heuristics work on Factorio
  (99.2%) but a language designed for index-then-resolve should make declarations syntactically
  distinguishable (e.g. template-ids always unambiguous, no most-vexing-parse). Recorded as an
  open design question in design.md.
- **Kov keywords must not break C++ corpora**: `accumulate`, `implicit`, `fallthrough`,
  `both_const`, `class_const` are contextual keywords in the parser.
- Macros are the one C++ feature a no-includes model cannot emulate from the outside: all the
  remaining parse errors and the project-side unresolved names come from macro-generated code.
- **Linking is not running.** Agui linked with 0 complaints and then crashed or computed zeros
  seven times over: static locals as allocas, reference globals as objects, lost out-of-line
  initializers of static data members, a non-const `this` in const methods, zero-initialised
  globals with default member initializers, a base-pointer adjustment skipped because both
  pointers are `ptr` in LLVM, and a `static` that reached the definition only when a call was
  emitted first. None of these shows in the typed percentage, the complaint count or the
  (then 36) tests; a program that exercises the converted code end to end is the regression check
  that matters, so every converted library gets one (smoke.kov, agui_smoke.kov).
- **Crash addresses resolve without a debugger**: the linker map (`--lib "-Wl,/MAP:file"`), a
  vectored exception handler printing the fault address and the stack slots that point into the
  image, and a script over the map give the function and its callers. Instrumenting the converted
  source with `printf` is free (convert.cmd regenerates it), and a probe against the standard
  library alone builds in seconds where one against CommonUtil + Agui took 1.5 minutes before the
  object cache warmed up.
